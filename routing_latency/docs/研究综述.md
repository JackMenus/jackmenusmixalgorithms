# 路由与延迟优化：前沿方向综述

> 本文是 `latency_routing` 库的理论背景。每节末尾标注「库中对应实现」，没有实现的部分标注为「仅文档」。
> 文献信息来自已发表的经典论文和公开资料，撰写时只做了有限的在线核对；引用前请自行确认年份与卷期。

## 1. 智能订单路由（SOR）

### 1.1 问题形式化
碎片化市场里同一标的在多个场所（交易所、ATS、暗池）报价。路由要回答三个问题：**去哪儿、发多少、用什么单型**。
目标通常是最小化「执行成本 = 价差/冲击 + 费用 − 返佣 + 未成交的机会成本」。

### 1.2 Cont & Kukanov 最优挂单拆分（2017）
- 把「市价单 M + 各场所限价单 L_k」写成一个**凸随机优化**问题，成交量由队列位置 Q_k 与随机流出量 ξ_k 决定。
- 关键结论：只有欠成交惩罚 λ_u 超过 半价差+吃单费 时才用市价单；在流动性不确定时，**最优解会超额挂单**（总挂单量 > 目标量），用超成交惩罚 λ_o 控制。
- 求解：随机逼近（Robbins–Monro）或样本平均近似。
- **库中对应**：`sor/cont_kukanov.py`（SAA + 投影次梯度），`urgency_to_penalty` 把挂单策略的 urgency 与因子 alpha 映射成 λ_u。

### 1.3 暗池/隐藏流动性的在线学习路由
- Ganchev, Kearns, Nevmyvaka, Vaughan（2010，"Censored exploration and the dark pool problem"）：暗池成交量只能被「截断观测」，用截断数据的 Kaplan–Meier 估计 + 探索/利用分配。
- Agarwal, Bartlett, Dama（2010）将其推广到对抗式在线学习。
- 近年工业实践：把每个场所的成交概率、逆向选择（成交后价格走势，markout）作为 bandit 的回报，按 Thompson Sampling/UCB 动态调整权重。
- **库中对应**：仅文档。`VenueQuote` 预留了每场所参数，可在集成层用 bandit 更新 `quote_update_rate`、费用调整后的有效价格等。

### 1.4 强化学习执行与路由
- Nevmyvaka, Feng, Kearns（2006）最早把 RL 用于最优执行。
- 近年的深度 RL 执行（如基于 PPO/DQN 的执行代理，以及在 ABIDES 等多智能体模拟器中训练）是热点，但在真实路由中的主要难点是**仿真到实盘的偏差**和**延迟随机性**。
- **库中对应**：`sim/` 可作为 RL 环境的雏形；路由器本身保持确定性与可解释，RL 建议只在上层调 urgency。

## 2. 延迟套利与「感知延迟」的路由

### 2.1 狙击问题（sniping）
- Budish, Cramton, Shim（2015, QJE）：连续限价簿 + 公共信号 → 速度竞赛，做市商为被狙击风险收取更宽价差。
- Aquilina, Budish, O'Neill（2022, QJE）用伦敦证券交易所消息数据量化：延迟套利竞赛非常频繁，单场竞赛的胜负差在**微秒级**，它构成了相当比例的成交量与有效价差。
- 推论：跨场所扫单时，**先到达的子单就是给对手的信号**。

### 2.2 同步到达（THOR 类）
- RBC 的 THOR（约 2010 年）按各场所延迟错开发送，使订单近乎同时到达，显著提高跨场所扫单的成交率。（专利中常见名称为 "transmission latency leveling"。）
- IEX 的 350µs 「speed bump」与 Crumbling Quote 信号则是交易所侧的对应方案。
- 本库改进点：不只按均值对齐，而是在**随机延迟（含突刺尾部）**下，按共同分位数对齐并用蒙特卡洛最大化「全部子单落在对手反应窗口内」的概率。
- **库中对应**：`sor/sync_send.py`；`sim/latency_arb_sim.py` 演示：在 150µs 反应窗口下，同步发送平均成交率约 92%，立即发送约 11%（见 `examples/demo.py` 输出，属于合成数据下的结果）。

### 2.3 报价陈旧风险
- 我们看到的报价在订单到达时可能已经失效。若报价刷新近似泊松（强度 λ），存活概率 = E[exp(−λL)]。
- 延迟越重尾，存活概率越低，路由应**按分位数或分布**而不是均值决策。
- **库中对应**：`sor/stale_quote.py`，被 `sweep_allocate` 用于折算可成交量和同价场所排序。

### 2.4 延迟的经济价值
- Moallemi & Saglam（2013, "The cost of latency in high-frequency trading", Operations Research）：在一个执行模型里推导出延迟成本与波动率、价差的关系，可用来评估「为降低 X 微秒是否值得花钱」。
- **库中对应**：仅文档；可用 `sim/` 做数值版评估。

## 3. 延迟建模与测量

| 主题 | 要点 | 库中对应 |
|---|---|---|
| 分布形状 | 右偏、多峰、重尾（中断、GC、交换机排队、撮合排队）；不能用高斯 | `VenueLatencyModel`：对数正态主体 + 突刺尾部混合 |
| 在线分位数 | 热路径上不能存样本：P²（Jain & Chlamtac 1985）、t-digest、HdrHistogram | `P2Quantile` |
| 漂移 | 网络拥塞会让分布整体漂移 → EWMA + 突刺检测 | `VenueLatencyModel(halflife=…)` |
| 时钟同步 | PTP（IEEE 1588）+ 硬件时间戳可达几十纳秒级；软件侧用 NTP 四时间戳 + 取最小 RTT 样本 | `estimate_clock_offset` |
| 合规 | 欧盟 MiFID II RTS 25 对高频交易要求与 UTC 偏差不超过 100µs、时间戳精度 1µs | 仅文档 |

## 4. 低延迟系统工程

### 4.1 内核旁路（kernel bypass）
- **思路**：绕过内核协议栈，用户态直接读写网卡环形缓冲，消除系统调用、上下文切换与中断。
- 常见方案：AMD/Solarflare **Onload**（兼容 socket API）与 **ef_vi**（更底层）、**DPDK**、**RDMA/RoCE**、Exablaze/Cisco 低延迟网卡；以及 Linux 的 **AF_XDP** 作为较轻量的选项。
- 配套：`isolcpus` / `nohz_full` 隔离核、IRQ 亲和性、关闭 C-state 与超线程、大页内存、忙轮询。
- **库中对应**：仅文档（这些属于部署层，Python 无法体现）。

### 4.2 无锁数据结构
- 单生产者单消费者环形队列是行情→策略→下单流水线的骨干。要点：2 的幂容量、单调指针、acquire/release 内存序、读写指针分 cache line、缓存对方指针。
- LMAX Disruptor 把这一模式推广到多消费者流水线（序号屏障）。
- **库中对应**：`infra/ring_buffer.py`（逻辑参考）与 `cpp/spsc_ring.hpp`（生产可用的 header-only 实现）。本机测试：约 5 ns/条、1.9 亿条/秒（4 核云容器，未绑核，仅作量级参考）。

### 4.3 FPGA 与硬件加速
- 典型架构：网卡 PHY/MAC → 行情解码（如 ITCH/OUCH、各交易所二进制协议）→ 订单簿 → 预计算的触发规则 → 直接组装下单报文。
- 公开资料中 FPGA tick-to-trade 已在**几十到一百纳秒级**；软件 + 内核旁路通常在**单位微秒级**。
- 关键技巧：**软件预计算、硬件触发**（CPU 计算好「如果价格到 X 就发单 Y」，FPGA 只做比较与发送）；报文模板预填充，只在最后写入价格/数量；甚至在报文头部先发出、根据后续字节决定是否中止。
- **库中对应**：仅文档。本库的路由结果（`ChildOrder` 列表 + `send_delay_us`）可以作为预计算模板交给硬件层。

### 4.4 物理链路
- 微波/毫米波链路比光纤快约三分之一（光在光纤中约为真空光速的 2/3）；例如芝加哥—新泽西走廊上，微波单程比光纤快数毫秒。
- 托管（co-location）：同机房内还会做**等长线缆**保证公平，但交换机端口、机柜位置仍造成纳秒级差异。
- **库中对应**：场所延迟的先验可在 `VenueLatencyModel(default_us=…)` 中设定，或者直接喂入测量值。

## 5. 与其他库的衔接

- **因子挖掘库 → 路由**：短期 alpha（`alpha_bps`, `alpha_horizon_us`）。alpha 越强、衰减越快，错过成交的机会成本越高 → λ_u 越大 → 更多吃单、更积极地同步扫单。
- **挂单策略库 → 路由**：`urgency`、限价、母单数量。挂单库决定「何时下多少」，路由库决定「去哪里、怎么发」。
- **路由 → 挂单策略库**：`RoutingDecision.diagnostics` 中的期望成交率、超额挂单量、同步成功概率，供挂单策略决定是否撤单重挂。
- **执行回报 → 路由**：用 `observe_latency` 持续更新延迟模型（下单→确认的单程延迟）。

## 6. 可继续扩展的方向
1. 用 bandit 按 markout 学习各场所的「真实」成交质量（1.3 节）。
2. 用 Hawkes 过程替换 `default_outflow_samples`，让 Cont-Kukanov 的流出量随订单流自激。
3. 把 `sync_send` 推广为「部分同步」：允许一部分子单晚到，换取更短的总完成时间。
4. 以 `sim/` 为环境训练 RL 执行代理，只输出 urgency，路由器保持确定性。
